### 1.1 진단 정정 (2026-08-22, 2회차에서 실측 후)

계측기를 고치고 실제로 재보니 **§1의 문제 목록은 그대로 유효하지만, 거기서
암묵적으로 전제했던 "그래서 DoD 품질이 나쁘다"는 사실이 아니다.**

`EXP_Result_3_Laundry_Actual_vs_Gold.md`(2026-08-20)는 세탁소 시나리오에서 URL
명시율 0/39(FAIL)을 기록했다. 같은 입력·같은 프롬프트로 다시 측정한 결과:

| 모델 | 회차 | DoD | URL 명시율 | 역량서술 | 체언종결 | 원자성 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| gpt-4o (프로덕션) | 1 | 38 | 100% | 0% | 100% | 100% |
| gpt-4o (프로덕션) | 2 | 29 | 93.1% | 0% | 100% | 96.6% |
| gpt-4o-mini | 1 | 23 | 95.7% | 0% | 100% | 100% |
| gpt-4o-mini | 2 | 24 | 79.2% | 0% | 100% | 100% |

**URL 문제는 재현되지 않는다.** 2026-08-19~20의 프롬프트 수정
(`0d9eedd`, `edde06f`)으로 이미 해결되었고, `EXP_Result_3`은 그 이전 상태를
기록한 낡은 문서다. 계측기가 고장나 있었기 때문에 **고쳐졌다는 사실 자체를
확인할 방법이 없었다.** 이것이 "이틀간 진전 없음"의 상당 부분을 설명한다:
이미 고친 문제를, 갱신되지 않은 실패 리포트를 보며 계속 고치고 있었다.

또한 URL이 없다고 잡힌 나머지 문장들은 대부분 정당하게 경로가 없는 것들이다
(상태 전이, 버튼 연타 등). 규칙 위반이 아니다.

**대신 실측에서 드러난 진짜 문제는 재현성이다.** 동일 입력·동일 온도(0.2)에서
gpt-4o가 DoD를 38개 → 29개로 생성했다. 30% 가까운 커버리지 변동이며,
`EXP_Result_3`이 지적한 "누락된 엣지 케이스"의 실체도 규칙 미준수가 아니라
이 변동일 가능성이 크다.

**따라서 우선순위를 바꾼다.** 규칙 준수율은 이미 목표를 넘겼으므로 D단계의
프롬프트 규칙 손질은 후순위로 내리고, 다음 두 가지에 집중한다.
- **생성 재현성**: 같은 입력에서 커버리지가 흔들리는 정도를 지표화하고 줄인다
- **B단계(검수 가능성)**: DoD가 실제로 실행 가능한 스펙이 되는 비율. 여전히 미측정이며 이것이 진짜 병목이다

## 2. 단계

- **A. 계측기 수리** — 정직한 DoD 지표 + 지표 자체의 단위 테스트 + 생성 결과 전문 보존 + 프롬프트 단일화
- **B. 검수 가능성 계측** — DoD → 계약 분석 → 질문 자동응답 → atom 조합 → 엄격 파서. `automation_ready` 도달률과 거부 사유 분포. 네트워크는 OpenAI만 필요
- **C. 판정 정확도 계측** — 픽스처 앱 정상판/고장판에 조합된 스펙을 실제 실행. False FAIL / False PASS 측정
- **D. 지표 기반 개선 반복** — A~C 지표를 보며 프롬프트·조합 규칙·atom 어휘를 고침

## 3. 성공 기준

baseline을 먼저 측정하고, 아래를 만족하면 정지한다.

| 지표 | 목표 | baseline (2026-08-22) | 현재 |
|---|---|---|---|

| 역량 서술('~가능함') 비율 | ≤ 5% | **0%** | 달성 |

### 2026-08-22 (3회차) — B단계 첫 측정과 최대 병목 제거

**`automation_ready` 도달률을 처음으로 측정했다.** `eval/run-composition-eval.mjs`가
프로덕션 저장 경로(`upsertCriteriaForMilestone`)와 같은 순서를 그대로 따른다:
계약 분석 → 질문 자동 응답(추천 선택지 채택) → 프리셋 → atom 조합 → 상태 확정.

첫 측정에서 거부 사유가 `llm_declined` 0건 / `schema_rejected` 전량으로 나왔다.
"이 조건은 자동화할 수 없다"가 아니라 **모델이 만든 조합을 파서가 버리는 것**이므로
어휘 부족(§21.3)이 아닌 고칠 수 있는 문제였다.

거부 지점을 짚기 위해 진단을 추가했다(`ComposeOutcome.detail`). 판정에는 쓰지 않고
어느 step의 어느 값이 걸렸는지만 남긴다. 그 결과 원인이 한 가지로 모였다:

> 모델이 `targetKind=field`에 `textbox`(역할 이름), `companyName`·`inviteEmail`·`file`
> (일반 입력란 이름)을 넣고 있었다. `field`는 로그인 요소 세 개(email/password/submit)
> 전용이므로 전부 거부되었고, **이것이 전체 DoD의 40%를 사람 확인으로 떨어뜨리고 있었다.**

**고친 방식**: 비슷한 대상으로 바꿔치기하지 않았다. `field=companyName`을
`label="companyName"`으로 고쳐 쓰면 한국어 라벨("회사명")과 맞지 않아 정상 앱을
실패로 판정한다. 대신 대상 지정을 종류별 필드로 나누고(`targetField`/`targetRole`/
`targetText`) 스키마에 열거값을 걸어 **잘못된 값을 애초에 만들 수 없게** 했다.
어휘를 벗어나면 조합 전체를 버리고 사람 확인으로 넘긴다(CLAUDE.md §11).

| 측정 | automation_ready | 비고 |
|---|---|---|
| 최초 (20개) | 45% | 진단 추가 전 |
| 진단 추가 후 (20개) | 60% | 코드 변경 없음 — 순수 편차 |
| 어휘 강제 후 (20개) | **80%** | 같은 20개 기준 |
| 어휘 강제 후 (74개) | 52.7% | 표본이 달라 위와 비교 불가 |

**이 상승을 개선으로 확정하지 않는다.** 코드를 바꾸지 않은 두 회차가 45%→60%로
흔들렸으므로 단일 실행의 차이는 편차와 구분되지 않는다. 다음 회차에서 반복 실행
지원을 넣어 노이즈와 분리한다.

남은 거부 지점(20개 기준 4건): `expect_visible` 대상 없음 3건, `fill`인데 입력값
없음 1건. 둘 다 프롬프트로 고칠 수 있다.

- 테스트 57개 통과(신규 6개는 어휘 이탈을 바꿔치기하지 않고 거부하는지 고정)
- 누적 OpenAI 추정 비용: 약 $0.15

### 2026-08-22 (4회차) — C단계 개통, 판정 정확도 첫 측정

**반복 측정을 넣었다**(`--runs N`). 코드를 바꾸지 않은 두 실행이 45%와 60%로 갈렸던
전례가 있어, 단일 실행의 차이를 개선으로 읽지 않기 위해 평균과 함께 최소·최대·폭을
낸다. 40개×3회로 잰 baseline은 **평균 67.5%, 폭 10%p**다.

**C단계를 개통했다.** 픽스처 앱(`eval/fixtures/todo-app/`)은 결함을 환경변수로 켜는
한 벌이며, 정상판과 고장판이 항상 같은 코드를 공유한다. 판정은 프로덕션 하네스를
그대로 쓰고 playwright 경로와 포트 두 곳만 치환한다(치환 실패 시 중단).

**첫 측정에서 러너 버그를 먼저 잡았다.** False FAIL이 62.5%로 나왔는데, 원인은
프로덕션이 하는 `compileManagedBrowserSpecToAtoms` 단계를 평가 러너가 빠뜨린 것이었다.
v1 프리셋 스펙에는 `steps` 배열이 없어 하네스가 즉시 오류를 냈다. 제품 결함으로
보고하기 전에 확인해서 바로잡았다. 교정 후 실측:

| 지표 | 목표 | 측정값 |
|---|---|---|
| 실행 가능한 스펙 | — | 87.5% (7/8) |
| **False FAIL** | 0% | **28.6%** (2/7) |
| False PASS | ≤ 10% | **16.7%** (1) |

**두 오판의 원인이 하나였다.** 조합기가 계약의 `precondition`을 무시한다.

- `session-persist`: 계약에 `precondition: 로그인한 상태`가 있는데도 조합은
  `goto(/todos) → expect_path(/todos)`뿐이다. 로그인하지 않았으니 정상판은
  `/login`으로 리다이렉트되어 **실패**하고, 고장판은 `no_auth_guard` 결함으로
  `/todos`가 열려 **통과**한다. 즉 같은 누락이 False FAIL과 False PASS를 동시에 만든다.
- `todo-check`: 계약에 `precondition: 할 일 목록에 할 일 존재`가 있는데 할 일을
  만드는 단계가 없어 체크박스를 찾지 못한다.
- 반면 `todos-auth-guard`(`precondition: 로그인하지 않은 상태`)는 올바르게 동작한다.

**조합기는 "로그인하지 않은 상태"는 지키고 "로그인한 상태"·"데이터 존재"는 무시한다.**
프롬프트에 지시가 있는데도 따르지 않으므로, 다음 회차에서 전제를 만들지 않은 조합을
거부 대상으로 삼아 교정 왕복에 태우는 방식을 시도한다(추측으로 로그인 단계를 끼워
넣지 않는다 — 틀린 전제를 만들면 오판이 늘어난다).

**측정 편차의 정체를 찾아 제품 결함 하나를 고쳤다.** 교정 왕복을 넣은 뒤 평균은
67.5%→80%로 올랐지만 폭이 10%p→**52.5%p**로 폭발했다(47.5/92.5/100). 2회차를 파보니
거부는 1건뿐인데 `analysis_failed`가 20건이었다. `analyzeDodContracts`가 요청 전체를
한 호출에 담고 응답 개수가 맞지 않으면 배치 전체를 throw하고 있었다. 상한이 100개이므로
**완료조건 100개가 한 번에 분석을 잃을 수 있는 실제 제품 결함**이다. 조합 단계가 이미
쓰던 방식(작게 나눠 담고, 잘리면 절반으로 재시도)을 분석기에도 적용했다.

### 2026-08-22 (5회차) — False PASS 0% 달성, 오판 원인이 분석기 단계로 확인됨

**측정 확정**: 청킹 후 automation_ready 평균 68.3%(폭 7.5%p). baseline 67.5%(폭 10%p)와
비교하면 **교정 왕복은 자동화율을 올리지 못했다.** 편차 폭 안의 차이이므로 개선으로
보고하지 않는다. 교정 왕복이 남긴 실제 가치는 거부 사유를 모델에 되돌리는 경로가
생겼다는 것이고, 청킹이 남긴 가치는 측정이 안정된 것이다(붕괴 회차 소멸).

**온도는 재현성의 원인이 아니다.** 프로덕션 `temperature: 0.2`를 0으로 낮추면 좋아질
것이라는 가설을 3회씩 측정해 기각했다.

| 온도 | DoD 개수 | 변동폭 |
|---|---|---|
| 0 | 37 / 36 / 31 | 16.2% |
| 0.2 (현재) | 35 / 38 / 34 | **10.5%** |

0이 오히려 나쁘다. 또한 3회 기준 변동폭 10.5%는 목표(≤15%) 안이므로, §1.1에 적은
31%는 2회 표본의 착시였다. **문장 품질 지표는 전부 목표 달성 상태다.**

**전제 강제로 False PASS를 없앴다.** 계약이 로그인 상태를 요구하는데 조합에 로그인
단계가 없으면 조합을 버린다. 로그인 단계를 임의로 끼워 넣지는 않는다 — 어떤 화면에서
어떻게 로그인하는지는 앱마다 다르고 틀린 전제는 오판을 늘린다.

| 지표 | 목표 | 4회차 | 5회차 |
|---|---|---|---|
| False PASS | ≤ 10% | 16.7% | **0%** ✅ |
| False FAIL | 0% | 28.6% | 26.3% ❌ |

**남은 False FAIL의 원인은 조합기가 아니라 계약 분석기였다.** `todo-add`의 계약을
보면 `precondition: "할 일 입력란에 텍스트 입력"` — 사전 상태가 아니라 행동이고,
`/todos`가 로그인을 요구한다는 정보가 없다. 원인은 `requiredContractFields`에서
`precondition`이 상태형 시나리오에만 필수였던 것이다. `form_submission`으로 분류된
완료조건은 **사전 상태를 사용자에게 묻지도 않았고**, 분석기가 채운 검증되지 않은 값이
그대로 쓰였다.

세 가지를 고쳤다.
1. `precondition`을 모든 시나리오의 필수 계약 필드로 승격 — 질문이 하나 늘지만
   잘못된 판정의 비용이 더 크다(CLAUDE.md §11)
2. 분석기 프롬프트에 "precondition은 상태이지 행동이 아니다"를 좋은 예·나쁜 예와 함께 명시
3. 제출 버튼에 `fill`을 쓰는 조합을 구조적으로 거부 — 하네스가 버튼에 입력을 시도하다
   실패해 정상 앱이 오류로 판정되고 있었다
