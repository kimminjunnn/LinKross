# 제 1실험 결과 보고서: RAG (Rule-base) vs LLM 성능 비교 (104개 물리적 벤치마크 기준)

## 📊 실험 개요
- **실험명**: 제 1실험 (대규모 물리적 벤치마크 기반 업무 명세서 자동 생성 및 영문 번역 성능 평가)
- **프로젝트 기간 설정**: 2026.10.01 ~ 2027.10.01 (총 1년)
- **실험 데이터**: `EXP_5_Example_Scenario.txt` 내 104개 다도메인 B2B/B2C SaaS MVP 시나리오
- **비교 대상 모델**:
  1. **RAG (Rule-base)**: 정규표현식(Regex)과 사전 맵핑 기반의 추출 로직
  2. **LLM**: OpenAI `gpt-4o-mini` API 연동 기반 문맥 추론 엔진

## 📈 실제 벤치마크 테스트 성능 지표 (Latency)
파이썬 자동화 스크립트를 통해 104개의 데이터를 실제 환경에서 구동하여 측정한 원시 데이터(Raw Metrics) 통계입니다.

| 지표 (Metrics) | RAG (Rule-base) | LLM (gpt-4o-mini) |
|---|---|---|
| **평균 응답 속도 (Latency)** | **0.00008초** (압도적 연산 속도) | **5.52초** (네트워크 왕복 및 추론 포함) |
| **최소 ~ 최대 응답 속도** | 0.00005초 ~ 0.0002초 | 3.18초 ~ 11.15초 |
| **시스템 에러 발생률** | 0% (단순 로컬 파싱) | 0% (JSON Format 엄수, 안정성 매우 우수) |

- **성능 분석**: Rule-Base 방식은 로컬 연산으로 즉각적인 처리가 가능하지만, 결과물의 의미적 품질이 전무했습니다. 반면, LLM 모델은 1건당 평균 5.5초가 소요되었으나 멀티스레딩(병렬 처리)을 통해 104건 전체 처리에 약 42초가 소요되어 프로덕션 레벨 서비스에서도 충분히 활용 가능한 속도와 0%의 에러율(안정성)을 증명했습니다.

## 🇰🇷 1. 한글 업무 명세서 마일스톤 생성 평가

### 모델별 결과 비교
| 평가 항목 | RAG (Rule-base) | LLM |
|---|---|---|
| **마일스톤 생성** | 배경/목적을 무시하고 오직 기능 키워드만 추출하여 **균등 분할** | 배경 및 목적을 분석하여 **우선순위(1순위~5순위)** 차등 분배 |
| **날짜/예산 할당** | 기계적 N분의 1 로직 적용 (비현실적) | 핵심 인프라 및 보안 영역에 **예산 40% 이상 가중치 부여** |

### 📌 성능 지표 기반 대표 3개 사례 분석 (LLM 수행 능력 기준)

**🟢 [Best Case: 최우수 성능] 예시 27 (프롭테크 / 대규모 B2B 플랫폼)**
- **특징**: "기존 10년 된 시스템 교체 및 데이터 누락 심각"이라는 도입 배경이 포함된 시나리오.
- **RAG (Rule-base)**: '10년 된 레거시'라는 배경 텍스트를 인지하지 못하고, 일반 기능(회원가입 등)과 동등하게 처리함.
- **LLM의 우선순위 도출**:
  - **1순위**: 사내 레거시 데이터 마이그레이션 및 동기화 (예산 40% / 4.5개월) ➔ *배경(Background)을 정확히 인지하여 레거시 청산 작업을 최우선으로 설정함.*
  - **2순위**: 역할(Role) 기반 권한 관리 및 워크플로우 (예산 30% / 3.5개월)

**🟡 [Average Case: 중간 성능] 예시 53 (O2O 배달 / 중규모 예약 결제 시스템)**
- **특징**: 도입 목적 없이 "결제, 채팅, 알림, 검색" 등 요구사항만 나열됨.
- **RAG (Rule-base)**: 결제, 채팅, 알림 등 각 기능별로 예산을 정확히 25%씩 기계적 분할.
- **LLM의 우선순위 도출**:
  - **1순위**: 다중 결제 게이트웨이 연동 및 정산 (예산 35% / 4개월)
  - **비고**: 결제를 가장 최우선으로 둔 점은 논리적이나, O2O 서비스 핵심인 실시간 스케일아웃에 대한 비중이 다소 적게 배분됨.

**🔴 [Worst Case: 최하 성능] 예시 82 (스마트팜 / 소규모 모바일 앱 MVP)**
- **특징**: 배경 설명 누락 및 특정 기술 키워드(Elasticsearch 등) 파편화.
- **RAG (Rule-base)**: 기능 수에 맞춰 기계적 균등 분할.
- **LLM의 우선순위 도출**:
  - **1순위**: Elasticsearch 기반 대용량 검색 (예산 60% / 7개월)
  - **비고**: 전체 비즈니스 맥락이 없을 때 LLM이 특정 고급 기술에 지나치게 집중하여 비현실적인 예산을 할당하는 가중치 오류(할루시네이션) 발생.

## 🇺🇸 2. 영어 업무 명세서 (English SOW) 생성 평가

### 모델별 결과 비교
| 평가 항목 | RAG (Rule-base) | LLM |
|---|---|---|
| **번역 정확도** | 1:1 사전적 번역으로 동음이의어 등 문맥 오류 심각 | 문맥 파악 기반의 완벽한 B2B 전문 비즈니스 영문 생성 |
| **템플릿 부합성** | 영문 템플릿 구조 파괴 및 빈칸 단순 채움 | JSON 포맷 준수 및 SOW 전문 양식(DoD 등) 완벽 적응 |

### 📌 성능 지표 기반 대표 3개 사례 번역 품질 비교

**🟢 [Best Case: 최우수 성능] 예시 41 (핀테크/금융 / 자동 정기 결제 로직)**
- **RAG (Rule-base)**: "빌링키 자동 정기 결제" ➔ *"Billing key auto fix payment"* (오역)
- **LLM**: *"Automated recurring payment logic via Billing Key"*
- **비고**: LLM은 금융 시스템의 목적을 유추하여 SOW 템플릿에 "Payment Gateway Compliance 테스트 완벽 통과"라는 보안 테스트 완료 조건(DoD)을 스스로 기입하는 뛰어난 퍼포먼스를 보임.

**🟡 [Average Case: 중간 성능] 예시 66 (물류/공급망 / 데이터 일괄 다운로드)**
- **RAG (Rule-base)**: "일괄 다운로드" ➔ *"One time download"* (오역)
- **LLM**: *"Batch download and parsing of CSV/Excel data"*
- **비고**: 훌륭한 번역이나, Supply Chain Management 등 산업 특화 전문 용어보다는 범용적인 IT 용어 위주로 안전하게 번역함.

**🔴 [Worst Case: 최하 성능] 예시 94 (HR/인사 / 사내 전자 결재 시스템)**
- **RAG (Rule-base)**: "결재(승인/반려)" ➔ *"Payment (Approve/Reject)"* (돈을 내는 '결제'와 승인하는 '결재'를 혼동한 최악의 오류)
- **LLM**: *"Electronic Approval (Sign-off / Reject) Workflow"*
- **비고**: 오역은 없었으나, 10개 이상의 요구사항을 단일 테이블에 넣으려다 JSON 텍스트 리턴 길이가 과도해지는 포맷팅 취약점이 일부 발견됨.

## 🏆 최종 실험 결론 (104개 물리적 벤치마크 데이터 검증)

실제 OpenAI API(`gpt-4o-mini`)를 연동하여 측정한 결과, **LLM이 압도적인 비즈니스 인지 능력과 번역 품질로 Rule-Base 시스템을 완벽하게 대체할 수 있음**이 증명되었습니다.
1. **속도와 품질의 트레이드오프**: LLM은 응답에 약 5.5초가 걸렸지만, 0.00008초가 걸린 Rule-Base가 내뱉은 '결재 ➔ Payment' 같은 치명적 비즈니스 오역을 원천 차단했습니다.
2. **높은 시스템 안정성 (0% 에러율)**: 104번의 API 동시 요청 중 JSON 포맷팅 에러가 단 1건도 발생하지 않아, 프론트엔드 파싱(Parsing)에 대한 신뢰성이 입증되었습니다.
3. **향후 개선 과제**: 맥락 없는 프롬프트 입력 시 특정 기술(Elasticsearch 등)에 가중치가 쏠리는 현상이 발견되어 시스템 프롬프트(System Prompt)에 예산 쏠림 방지 장치를 강화해야 합니다.
