# 제 3실험 결과 보고서: EXP_7(세탁소 픽업-배송) 실제 생성 결과 vs 골드 스탠다드 대조 (EXP_Result_3.md)

`EXP_7_Laundry_Pickup_Delivery.md`의 입력 프롬프트를 실제 SOW 생성 화면에 넣어 나온 결과(M1~M7, 7개 마일스톤 / 39개 DoD)를 골드 스탠다드와 대조한 결과입니다.

---

## 📊 규칙 준수 여부 요약 (`analyze.ts` 5대 필수 규칙 기준)

| 규칙 | 판정 | 근거 |
|---|---|---|
| ① 화면 단위 분할 / 기술 용어 금지 | ✅ PASS | DB, API 등 백엔드 용어 없음. 화면·행동 단위로 구성됨 |
| ② 마일스톤 5~7개 | ✅ PASS | 정확히 7개 |
| ③ 엣지 케이스 개별 DoD 분리 | ⚠️ 부분 PASS | 문장 단위 결합은 없으나, **원문에 명시된 엣지 케이스 자체가 다수 누락**(아래 §2 참고) |
| ④ 정확한 URL 라우팅 명시 (`/login` 등) | ❌ **FAIL (0/39)** | 39개 DoD 전부 "화면", "목록", "상세"처럼 추상 명사만 사용, URL이 단 한 곳도 없음 |
| ⑤ 명사형 종결 (`~됨/~함/확인`) | ⚠️ 표면 PASS, 실질 미흡 | 종결어미는 지켰으나 대부분 "~가능함" 형태의 **역량 서술**이라 Playwright 액션+검증 시나리오로 바로 옮기기 어려움(아래 §3 참고) |
| ⑥ 예산 차등 분배 | ✅ PASS | 10k/8k/15k/20k/12k/12k/22k(총 99k), 균등(≈14.1k)이 아니라 M4·M7에 가중치 부여 |
| ⑦ 범위 보존 | ✅ PASS | 원문에 없는 QA/배포 작업 임의 추가 없음 |

**총평: 5개 규칙 중 2개는 완전 통과, 1개는 완전 실패(④), 2개는 "형식은 지켰지만 실질이 비어있는" 상태(③⑤).** 이전 `SOW_PERFORMANCE_METRICS.md`에서 "100% 달성"으로 기록된 URL 라우팅 규칙이 이번 실행에서는 완전히 재발했다는 점이 가장 중요한 발견입니다.

## 🔍 1. Rule ④ URL 라우팅 100% 누락

골드 스탠다드는 모든 DoD에 `/signup`, `/orders/[id]`, `/admin/orders` 같은 구체 경로를 명시했지만, 실제 결과는 39개 DoD 어디에도 경로가 없습니다.

| 골드 스탠다드 (M1) | 실제 생성 결과 (M1) |
|---|---|
| `/signup`에서 이메일·비밀번호 입력 후 가입 완료 시 `/login`으로 이동됨 | 고객이 이메일과 비밀번호로 회원가입 가능함 |
| `/login`에서 존재하지 않는 이메일 입력 시 "가입되지 않은 계정입니다" 오류 메시지가 표시됨 | 존재하지 않는 계정으로 로그인 시 오류 메시지 노출됨 |

`SOW_PERFORMANCE_METRICS.md`가 "UI 라우팅 명시율: 0% → 100%"로 기록했던 개선이 이번 실행에서는 반영되지 않았습니다. 시스템 프롬프트(`analyze.ts` 규칙 4)에는 여전히 명시되어 있으므로, **모델이 규칙을 일관되게 지키지 못하는 재현성 문제**로 보입니다.

## 🔍 2. 원문에 명시된 엣지 케이스 중 누락된 것

입력 프롬프트(§7, §14, §15, §4)에 명시적으로 요구된 항목인데 39개 DoD 어디에도 없는 것들입니다.

| 원문 근거 | 요구된 엣지 케이스 | 실제 결과 반영 여부 |
|---|---|---|
| §7 주문 취소 | "픽업 완료 이후 단계는 고객이 직접 취소 불가, 관리자 문의 안내" | ❌ 없음 (M6은 "픽업 대기" 취소 성공 케이스만 있음) |
| §4 상태 파이프라인 | "픽업 대기에서 배송 완료로 바로 건너뛸 수 없음"(잘못된 전이 시도 시 거부) | ⚠️ "정해진 순서대로만 진행됨"이라는 추상적 문장 1개뿐, 구체적 실패 시나리오 없음 |
| §14 권한과 보안 | "다른 고객의 주문에는 URL을 직접 입력해도 접근 불가" | ❌ 완전 누락 |
| §14 권한과 보안 | "기사는 배정된 주문 외 조회 불가" | ⚠️ 긍정 케이스("배정된 주문만 조회 가능함")만 있고, 타 기사 주문 접근 시도 시 차단되는 부정 케이스 없음 |
| §14 권한과 보안 | "관리자 전용 화면은 관리자만 접근" | ❌ 완전 누락 (일반 고객의 관리자 화면 접근 차단 DoD 없음) |
| §15 오류 및 상태 처리 | "로딩 중 / 데이터 없음 / 요청 실패" 상태 구분 | ❌ 완전 누락 |

CLAUDE.md §11(테스트와 완료 기준)이 "비인가 프로젝트 접근"을 보안 검증의 필수 항목으로 명시하는데, 이번 결과에는 권한 경계 관련 DoD가 **7개 마일스톤 39개 중 단 1개**("기사는 배정된 주문만 조회 가능함", 그마저도 긍정 케이스만)뿐입니다.

## 🔍 3. "~가능함" 패턴: 명사형 종결의 형식적 충족

Rule ⑤는 "Playwright E2E 테스트 시나리오(액션+검증) 형태"를 요구하는데, 실제 결과의 상당수는 종결어미(`~함/~됨`)만 맞추고 액션·검증 요소는 빠진 **역량 서술문**입니다.

- "고객이 전체 주문 목록을 확인 가능함" → 어떤 화면에서, 무엇이 어떤 형태로 보이는지 불명확
- "특정 주문을 선택해 상태를 직접 변경 가능함" → 어떤 UI 조작으로, 상태가 어떻게 바뀌었다는 게 화면에 어떻게 드러나는지 불명확

골드 스탠다드처럼 "무엇을 클릭/입력하면 → 어떤 문구·상태·이동이 눈에 보이는가"가 있어야 발주자가 Preview에서 바로 검수할 수 있는데, 현재 형태는 검수 시 "이게 통과 조건을 만족했다고 어떻게 판단하나요?"라는 추가 질문이 필요합니다.

## 💡 4. 개선 제안

1. **URL 누락을 사후 검증 레이어에서 강제**: 시스템 프롬프트만으로는 재현율이 불안정하므로, `analyze.ts`의 응답 후처리 단계에서 DoD 문자열에 `` ` `` 또는 `/`로 시작하는 경로 패턴이 없으면 재생성을 요청하거나 "확인 필요"로 표시하는 검증 로직 추가를 고려해볼 만합니다(§21.3 갭 로그 파이프라인과 연결 가능).
2. **"~가능함" 금지 예시 추가**: 규칙 5의 나쁜 예로 "~한다/~된다"뿐 아니라 "~가능함"류의 역량 서술도 명시적으로 금지하고, "어떤 조작 → 어떤 관찰 가능한 결과"의 최소 2단 구조를 요구하는 문구를 프롬프트에 추가하는 것을 제안합니다.
3. **권한/보안 엣지 케이스 별도 강제 규칙화**: 현재 5대 규칙에는 권한 경계 테스트를 강제하는 항목이 없습니다. 원문에 "다른 사용자 접근 불가", "관리자만 접근" 같은 문구가 있으면 이를 반드시 별도 DoD로 뽑아내라는 규칙(가칭 "Rule 8: 권한 경계 테스트 강제")을 추가하면 이번 케이스의 §14 누락을 방지할 수 있습니다.
