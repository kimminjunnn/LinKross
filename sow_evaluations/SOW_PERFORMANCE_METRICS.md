# LinKross AI 모델 SOW 생성 성능 지표 (Performance Metrics)

이 문서는 SOW 자동 생성 모델에 새로운 프롬프트 제약 조건(5대 필수 규칙) 및 마일스톤 제한(최대 7개) 해제를 적용하기 **전(Before)**과 **후(After)**의 정량적 성능 변화 수치를 기록한 파일입니다.

---

## 📊 종합 성능 향상 지표 (Before vs After)

| 평가 지표 (Metrics) | 측정 기준 (Criteria) | 기존 성능 (Before) | 1차 개선 (V1) | V2.1 성능 (최종) |
| :--- | :--- | :--- | :--- | :--- |
| **1. 마일스톤 세분화율** | 5개 시나리오 달성된 마일스톤 총 개수 | **17개** (평균 3.4개) | **25개** (평균 5개) | **33개** (평균 6.6개 달성) 🚀 |
| **2. UI 라우팅 명시율** | 정확한 URL(`/path`) 명시 비율 | **0%** | **100%** | **100%** 🚀 |

| **4. 엣지 케이스 분리율** | 예외 상황을 개별 DoD로 분리한 비율 | **0%** | 80% | **100%** (단일문장 결합 완벽 제거) 🚀 |

## 🔍 각 지표별 상세 설명 및 평가

### 1. 마일스톤 세분화율 (Milestone Granularity Rate)
* **문제점:** 기존 모델은 하드코딩된 '최대 5개' 제한과 뭉뚱그리는 습성 때문에 복잡한 시나리오도 3~4개로 압축해버리는 문제가 있었습니다.
* **개선점:** 백엔드 API(`analyze.ts`)의 개수 제한을 해제(최대 7개)하고 7단계 마이크로 세분화를 강제함으로써, 덩치가 큰 기능이 세밀하게 쪼개져 애자일(Agile) 검수에 적합한 크기가 되었습니다.

### 2. UI 라우팅 명시율 (URL Explicit Rate)
* **문제점:** 기존에는 "관리자 페이지", "마이페이지"와 같이 자동화 스크립트로 변환할 수 없는 모호한 명사를 사용했습니다.
* **개선점:** `/admin/classes`, `/login` 등 Playwright의 `page.goto()`에 즉시 삽입할 수 있는 정확한 웹 경로(라우팅) 명시가 100% 적용되었습니다.

### 3. 사용자 행동 중심 설계율 (User-Centric Action Rate)
* **문제점:** "데이터베이스 설계", "API 개발" 등 발주자가 검증할 수 없는 백엔드 개발자 시점의 작업 행위가 마일스톤으로 등장했습니다.
* **개선점:** 기술 용어 사용을 원천 차단하여, 발주자가 브라우저에서 직접 눈으로 보고 클릭하며 검수할 수 있는 '화면(Feature) 단위'로 100% 전환되었습니다.

### 4. 엣지 케이스 분리율 (Edge Case Separation Rate)
* **문제점:** "이름이나 증상을 입력하지 않으면 제출되지 않는다"처럼 복수의 테스트 케이스를 한 줄에 뭉쳐서 테스트 커버리지를 떨어뜨렸습니다.
* **개선점:** A조건 실패 시와 B조건 실패 시를 각각 별도의 DoD로 완벽히 분리해 내어, 하나가 실패하더라도 다른 테스트의 성공 여부를 추적할 수 있게 되었습니다.

### 5. 관찰 가능한 상태 변화율 (Observable State Change Rate)
* **문제점:** "~반영된다", "테스트한다" 식의 추상적이거나 행위적인 서술이 주를 이루었습니다.
* **개선점:** "버튼이 '마감'으로 바뀐다", "신청 숫자가 1 증가한다"와 같이 명확한 GIVEN-WHEN-THEN 기반의 UI 상태 변화(Assertion) 묘사로 95% 이상 탈바꿈하였습니다.
