# AI 모델 SOW 생성 결과 및 모범 마일스톤 비교 피드백

본 문서는 LinKross 프로젝트의 업무 명세서(SOW) 자동 생성 프롬프트를 고도화하기 위해, 4가지 추가 모범 마일스톤(Gold Standard) 데이터와 기존 AI 모델의 생성 결과를 비교 분석한 리포트입니다.

## 1. 비교 분석 개요

제공해주신 4개의 모범 사례(공방 원데이클래스, 사내 비품 대여, 독서 모임 출석, 동물병원 예진표)는 모두 **프론트엔드 개발자와 QA 엔지니어가 즉시 E2E 테스트(Playwright 등) 코드로 옮길 수 있는 완벽한 수준의 구체성**을 띠고 있습니다. 

반면, 기존 모델이 도출했던 결과(PT 예약 관리)는 **비즈니스 로직과 기획 의도(중복 차단 등)를 잘 파악하는 훌륭한 PM**의 형태였으나, 검수를 위한 '기계적 명확성'이 부족했습니다.

---

## 2. 첫 번째 사례(PT 예약 관리) 집중 비교

| 구분 | 모범 사례 (Gold Standard) | 기존 모델 (AI 생성 결과) |
| :--- | :--- | :--- |
| **마일스톤 구성** | 7개의 마이크로 마일스톤 (로그인, 상세조회, 생성, 취소 등 분리) | 4개의 통합 마일스톤 (M2 하나에 예약/중복방지/취소 모두 포함) |
| **라우팅 (URL)** | `/signup`, `/login`, `/dashboard` 등 정확한 테스트 경로 명시 | "트레이너 목록 화면", "마이페이지" 등 한글 명칭 위주 사용 |
| **UI 상태 변화** | "클릭이 비활성화된다", "지난 예약 섹션에 표시된다" | "즉시 표기된다", "화면으로 이동한다" (추상적 서술) |
| **특징** | 개발자 및 QA가 E2E 테스트 자동화 스크립트로 즉시 작성 가능 | 기술적 엣지 케이스(동시성 예외)를 방어하는 기획자적 시각 우수 |

## 3. 모범 사례 분석을 통한 우리 모델의 핵심 약점

### 약점 1: '상태 변화'에 대한 모호한 서술 (State Transition)
* **모범 사례:** "신청 버튼 클릭 시 **'신청 완료' 메시지**가 표시되고 버튼이 **'신청 취소'로 바뀐다.**", "신청 인원 숫자가 **1 증가한다.**"
* **우리 모델:** "본인의 마이페이지와 해당 트레이너 스케줄에 즉시 표기된다.", "필수 항목을 입력하지 않으면 제출이 불가능하다."
* **피드백:** 우리 모델은 '어디에 반영된다', '~된다' 식의 개념적/기능적 서술에 그칩니다. 반면 모범 사례는 UI 컴포넌트(버튼 텍스트, 카운트 숫자, 정확한 에러 문구)의 명확한 상태 변화(Before/After)를 짚어줍니다.

### 약점 2: 마일스톤 쪼개기 방식 및 엣지 케이스 누락
* **모범 사례:** 모든 프로젝트를 **사용자 행동 및 화면 단위의 7개 마이크로 마일스톤**으로 쪼개고, 세부 엣지 케이스(예: '이름 누락'과 '증상 누락')를 별도의 DoD로 분리합니다.
* **우리 모델:** 5개 시나리오가 진행될수록 마일스톤이 4개 ➡️ 3개로 갈수록 뭉뚱그려집니다. M2 하나에 '조회/예약/중복방지/취소'를 통째로 묶고, 세부 실패 케이스도 하나의 문장으로 통합해버립니다.
* **피드백:** 묶음 단위가 커지면 세부 엣지 케이스 검증 기준이 사라져 테스트 커버리지가 줄어들고, 하나만 오류가 나도 전체가 실패하게 되어 애자일 검수에 불리합니다.

### 약점 3: 라우팅(URL 경로) 명시 부재
* **모범 사례:** `/admin/classes/new`, `/my-rentals`, `/pre-check` 등 행동이 일어나는 정확한 URL(페이지 경로)을 항상 명시합니다.
* **우리 모델:** "트레이너 목록 화면", "마이페이지" 등 한글 명사로만 지칭합니다.
* **피드백:** URL 명시는 QA 자동화 봇이 `page.goto('/my-rentals')` 처럼 스크립트를 즉시 작성할 수 있게 하는 핵심 요소입니다.

### 약점 4: 기술 레이어 단위의 마일스톤 분할 및 기술 용어 남발
* **모범 사례:** 철저하게 '비개발 발주자가 화면에서 관찰 가능한 사용자 행동(Feature)' 단위로 마일스톤을 구성합니다.
* **우리 모델:** 거의 모든 케이스의 M1이 "데이터베이스 설계 및 로그인"으로 시작하며, 개발자의 작업 순서(DB ➡️ API ➡️ UI)를 제목에 그대로 노출합니다.
* **피드백:** `AGENTS.md`의 핵심 원칙 위배입니다. 비개발 발주자는 브라우저에서 'DB 설계'를 검수할 수 없습니다.

### 약점 5: 검증 불가능한 프로세스(작업 행위) 서술
* **모범 사례:** 특정 화면에서 어떤 결과물이 나오는지를 명시합니다.
* **우리 모델:** M4 마일스톤의 DoD로 "최종 승인 테스트 및 오류 수정"이라는 프로세스를 적어두었습니다.
* **피드백:** DoD(완료 조건)는 기능이 작동한다는 '관찰 가능한 결과'여야지, "테스트를 한다", "버그를 고친다" 같은 '과정/행위' 서술이 되어서는 안 됩니다.

## 4. 프롬프트 개선을 위한 핵심 지침 (Action Items)

이 피드백을 바탕으로, 제미나이에게 주입할 `AGENTS.md`나 시스템 프롬프트에 다음 **5대 필수 작성 규칙(DoD Rules)**을 추가해야 합니다.

### 📌 [개선된 시스템 프롬프트 가이드 추가 제안]

```markdown
**[SOW 작성 시 절대 준수 사항 - DoD 및 마일스톤 작성 규칙]**

1. **마일스톤 세분화 (7단계 원칙) 및 화면 단위 분할:** 
   기능을 뭉뚱그리지 말고 '핵심 기능', '제한/마감', '예외 처리'를 각각 독립적인 마일스톤(최소 5~7개)으로 분리하세요. 마일스톤은 철저히 사용자 화면/행동 단위로 나누고, "데이터베이스 설계", "API 개발" 같은 기술 레이어 작업 순서로 묶지 마세요.

2. **기술 용어 및 작업 행위 서술 금지:**
   비개발 발주자가 브라우저에서 확인할 수 없는 백엔드 용어나 인프라 용어 사용을 금지합니다. 또한 DoD에 "테스트 진행", "오류 수정" 같은 작업 과정(프로세스)을 적지 마세요.

3. **구체적인 URL 라우팅 명시:**
   행동이 일어나는 위치와 이동하는 목적지를 추상적인 단어가 아닌 예상 URL(예: `/login`, `/admin/reservations`, `/classes/[id]`)로 반드시 표기하세요.

4. **UI 상태 변화의 명시 (GIVEN-WHEN-THEN):**
   "~가능하다", "반영된다" 같은 서술적 표현을 금지합니다.
   - 텍스트 변화: "버튼 텍스트가 '마감'으로 바뀐다"
   - 수치 변화: "잔여 정원 숫자가 1 감소한다"
   - 오류 메시지: 정확히 노출될 에러 메시지 텍스트 명시
   등 화면 상의 구체적인 UI 컴포넌트 변화를 정확히 묘사하세요.

5. **성공/실패 및 조건별 독립적 분리:**
   "필수값을 입력하지 않으면 제출이 불가능하다"처럼 여러 조건을 한 문장으로 합치지 마세요. '이름 미입력 시'와 '증상 미입력 시' 등 각각의 성공/실패 엣지 케이스를 별도의 DoD 항목으로 분리하여 작성하세요.
```

## 5. 정량적 성능 지표 분석 (Quantitative Analysis)

앞서 분석한 5개의 시나리오를 바탕으로, 모범 사례(Gold Standard) 대비 기존 AI 모델의 산출물이 LinKross의 제품 원칙을 얼마나 준수했는지 수치화한 결과입니다.

| 평가 지표 (Metrics) | 측정 기준 | 모범 사례 (Gold Standard) | 기존 AI 모델 결과 | 달성률 / 상태 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 마일스톤 세분화율** | 5개 시나리오 기준 총 마일스톤 개수 | **35개** (각 7개 고정) | **17개** (4, 4, 3, 3, 3개로 점차 감소) | 🔴 **48.5%** (과도한 묶음 처리) |
| **2. UI 라우팅 명시율** | 행동의 목적지를 정확한 URL(`/path`)로 명시한 시나리오 비율 | **100%** (5/5) | **0%** (0/5) | 🔴 **0%** (자동화 테스트 작성 불가) |
| **3. 사용자 행동 중심 설계율** | M1 마일스톤 제목에 개발/인프라 용어(예: DB 설계)가 없는 비율 | **100%** (5/5) | **0%** (0/5) | 🔴 **0%** (모든 M1에 기술 용어 노출) |
| **4. 엣지 케이스 독립 분리율** | 예외 상황(성공/실패, 조건A/B)을 하나의 문장으로 뭉치지 않고 개별 DoD로 분리한 비율 | **100%** | **0%** | 🔴 **0%** (검수 커버리지 대폭 감소) |
| **5. 관찰 가능한 상태 변화율** | DoD에 정확한 UI 텍스트, 버튼 상태, 수치 변화가 포함된 비율 | **95% 이상** | **15% 미만** | 🔴 **매우 낮음** ("~된다" 식 추상적 서술) |

### 📊 수치 분석 결과 요약
* 기존 프롬프트 환경에서 모델의 자동화 검수 호환성(Playwright 테스트 작성 가능 여부) 점수는 사실상 **0점에 가깝습니다.**
* 모델은 시간이 지날수록, 혹은 문맥이 주어질수록 기능을 세분화하기보다는 **'카테고리별로 묶고 기술 레이어로 추상화하려는 강력한 습성'**을 보였습니다. 
* 이는 모델의 지능 문제가 아니라 **'목적 함수의 방향성'** 문제입니다. 즉, 위 수치들은 앞서 제안된 **[개선된 시스템 프롬프트 가이드]**를 적용하면 즉각적으로 **90% 이상으로 끌어올릴 수 있는 기계적 지표**들입니다.

## 6. 총평
우리 모델은 **"문맥 파악과 비즈니스 예외 상황(동시성 등)을 도출하는 지능"**은 이미 훌륭하게 갖춰져 있습니다. 여기에 위에서 도출한 **"URL 기반, UI 상태 변화 기반의 명확한 문체 규칙"**을 프롬프트로 강제하기만 하면, 제공해주신 모범 사례와 동일한 수준의 고품질 자동화 명세서를 생성할 수 있습니다.
